# Virtual Fitting Room — Design (v1)

> **Status:** DRAFT for user review. Direction: **real-time live-camera 3D AR** for
> all categories. **No AI image generation.** Supersedes the exploration notes in
> `2026-07-01-virtual-tryon-brainstorm-checkpoint.md`.
> **Date:** 2026-07-01

## 1. Goal

A Wanna-style **Virtual Fitting Room**: the user picks a product category, the
camera opens, and they see themselves **wearing the product's 3D model live**,
tracked as they move — on their own device. Categories in v1: **eyewear, neck
accessories, wrist accessories, top clothing, bottom clothing** (+ **shoes** as a
phase-2 category via a dedicated foot tracker).

Non-negotiables established with the user:
- **Real-time live-camera 3D AR** — the user sees themselves in the camera wearing
  the actual product's 3D model. This is how Wanna works (3D model + tracking).
- **Absolutely NO AI image generation** (no diffusion/FASHN/server-rendered images).
- **Self-hosted; no paid try-on SaaS/API.** **Tripo3D** (image→3D API, 2,000 free
  signup credits + commercial rights) is the accepted tool for generating the 3D
  models. Accessed behind a provider-agnostic adapter so it can later be swapped for
  self-hosted TRELLIS.2 (MIT, free) at scale without a rewrite.
- "Make it work correctly," minimal-but-real, ~10-day window. Improve later.

## 2. Core approach (one engine, all categories)

> **Camera + the product's 3D model (Tripo3D GLB) + body-part tracking → rendered
> live on the user, entirely on their device.**

- **Rendering:** `three.js` via `@react-three/fiber` + `@react-three/drei`
  (GLB loading, fits the React/Next stack). Camera video is the scene background.
- **Tracking:** `@mediapipe/tasks-vision` on-device — `FaceLandmarker`,
  `HandLandmarker`, `PoseLandmarker`. Feet: `WebAR.rocks.hand` foot NN (MIT).
- **Assets:** one **GLB per product**, generated by **Tripo3D** (image→3D), cached
  on the CDN with anchor/scale metadata.
- **No server compute for try-on.** EC2 only serves the app, hosts GLBs, and runs
  the Tripo3D asset-gen + background-removal in the asset pipeline.

### The user's category-first flow (endorsed)
User selects a **category before the camera opens**. This decides which single
tracker to load (lighter/faster) and which anchor rules to apply.

| Category | Tracker | 3D placement | Quality |
|---|---|---|---|
| Eyewear | FaceLandmarker + 4×4 head matrix | nose/ear anchor, full 3D rotation, face-mesh occluder | Excellent |
| Neck accessories | Face / Pose | neck/collar anchor, scale by shoulder width | Good |
| Wrist accessories | HandLandmarker | wrist anchor, forearm orientation | Good (minor jitter) |
| Top clothing | PoseLandmarker | rig/pin GLB to shoulders–torso | Paper-doll (see §6) |
| Bottom clothing | PoseLandmarker | rig/pin GLB to hips–legs | Paper-doll (see §6) |
| Shoes (phase 2) | WebAR.rocks foot NN | foot anchor + orientation | Decent |

## 4. Data flow

- **Try-on (runtime, client-side):** pick category → open front camera → load the
  matching MediaPipe/WebAR.rocks model + the product's **GLB** (+ anchor metadata)
  from CDN → each frame: landmarks → compute transform (position/scale/rotation) →
  render GLB in the r3f scene over the video, with occluder where applicable →
  ~30fps. No backend round-trip beyond fetching the static GLB.
- **Asset prep (offline/batch):** seller photo → background removal → **Tripo3D
  image→3D** → GLB → normalize (scale/orient/center + define anchor) → CDN + metadata.

## 5. Asset strategy (the real bottleneck)

- Sellers upload flat photos, not 3D. **Tripo3D auto-generates the GLB** per product.
- **Clothing: feed Tripo3D BOTH front + back photos** (multi-image → 3D) so the back
  is real, not hallucinated — required for the turn-around effect (§6).
- **v1 = a curated showcase set** (a handful per category) with QA'd GLBs, to prove
  the end-to-end experience before scaling the pipeline.
- Image→3D is weakest on **thin/reflective** items (eyewear frames, shiny jewelry) →
  QA/curate; feed it clean, centered, plain-background photos.
- "Improve later": generate on product upload, QA queue, better inputs; optionally
  swap the provider adapter to self-hosted TRELLIS.2 (MIT, $0/model) for scale.

## 5b. Testing harness (build + validate BEFORE product-upload integration)

Goal: prove Tripo3D 3D quality + the AR try-on **now**, standalone, without touching
the product-upload flow. Reuses the existing **`MediaServing`** app
(`../MediaServing`, Fastify + S3 + BullMQ + Redis worker).

**Backend — new async "build model" job in MediaServing** (mirrors its existing
video-job pattern):
- **New endpoint** (e.g. `POST /tryon/models`) alongside `src/api/upload.js`:
  accepts **front + back + side** product images (multipart) + a `category`; streams
  them to S3; enqueues a BullMQ job. Auth via existing `API_KEY` middleware.
- **New queue + job** `src/services/tryonQueue.js` + handler (pattern of
  `videoQueue.js` / `videoJobs.js`), processed by `src/worker.js`.
- **New service** `src/services/modelGenService.js` — a **provider-agnostic adapter**
  ("image(s) in → GLB out"); current implementation `tripoProvider.js` calls the
  **Tripo3D image→3D API** (multi-image), polls until the GLB is ready, downloads it.
  Swappable later for a `trellisProvider.js` (self-hosted) with no caller changes.
- **Store the GLB in S3** via `src/storage/s3Client.js` under a dedicated folder
  (e.g. `tryon-models/<modelId>.glb`) + a small JSON manifest (category, anchor
  metadata, source image keys, status).
- **Status endpoint** (e.g. `GET /tryon/models/:id`) → `{status, glbUrl}` for polling.

**Frontend — standalone test page in Trydos** (dev/testing only, not the product page):
- A route (e.g. `app/(client)/[lang]/tryon-test/`) that lists built GLBs from the
  manifest, lets you **pick a model + category**, opens the front camera, and runs
  the same `components/products/tryon/` AR engine → live result.
- Lets the team eyeball quality per category/product and iterate on Tripo3D inputs
  (e.g. front-only vs front+back+side) before committing to the pipeline.

**Migration path (later, out of this testing scope):** once quality is validated,
move the "build model" trigger to **product upload/save** (seller dashboard), so
GLBs are generated automatically; the runtime AR engine is unchanged.

## 5c. Scaling path (phase 2, NOT in v1): self-hosted TRELLIS daily batch

When daily volume is real (~100 products/day ≈ 3,000/month), swap the adapter's
`tripoProvider` for a `trellisProvider` (self-hosted TRELLIS.2, MIT). Run it as a
**scheduled daily batch** (e.g. 09:00): boot a GPU instance, drain the day's queue
one-by-one, shut down.

- **Instance:** g5.xlarge (A10G 24GB), on-demand ~$1.006/hr (spot ~$0.35/hr).
- **One 24GB GPU = one TRELLIS job at a time** (VRAM-bound); concurrency = more
  instances = same GPU-hours, just faster. So cost ≈ total GPU-hours.
- **Time/day:** 100 models × ~30–120s + ~5 min cold start ≈ **1–3.5 hr/day**
  (benchmark seconds-per-model on the target GPU early).
- **Cost:** **~$20–60/month** (spot→on-demand), vs **~$750/month** for hosted
  pay-per-use (fal.ai $0.25/model) at the same volume → self-host wins ~$250–700/mo.
- **Ops (the real cost):** scheduled start/stop (EventBridge/cron), weights baked
  into an AMI/EBS snapshot (skip re-download), spot-reclaim retry (or use on-demand
  at this low daily cost), and per-job failure handling so a bad photo doesn't stall
  the queue.
- **Break-even vs hosted:** roughly **~1,000 models/month** — below that, stay on
  Tripo3D; above it, the daily-batch self-host is cheaper. The adapter makes this a
  drop-in change, no rewrite.

## 6. See the garment from all angles (turn around → see the back)

A first-class requirement: when the user turns, they see the garment's back/sides,
Wanna-style. This needs **3D geometry + rotation, NOT cloth simulation** (fabric
smoothness explicitly out of scope). Two pieces:

1. **Full 3D mesh with a real back.** A Tripo3D GLB is a full 360° mesh. Feeding it
   only the front photo makes it **hallucinate** the back → feed it **BOTH front and
   back product photos** (multi-image → 3D) for a correct back texture. Biggest
   quality lever; back-view listing photos usually already exist.
2. **Orientation tracking → rotate the whole GLB.** From PoseLandmarker 3D
   landmarks, compute torso **yaw** (shoulder vector L→R, stabilized by hip vector);
   rotate the entire mesh to match. Turn 180° → mesh turns 180° → back faces camera.
   This is rigid whole-mesh rotation — **no rigging required.**

Supporting polish (no cloth sim):
- **Body-segmentation occlusion** (MediaPipe body mask) so arms/torso hide garment
  parts behind them → solid at angles, not floating.
- **Landmark smoothing** (One-Euro filter) → no jitter while rotating.
- **Facing-away fallback:** Pose confidence drops when fully turned → hold last known
  orientation to avoid flicker.

## 6b. Known quality limit — clothing

The garment **rotates as a whole**. Standing and turning to see front/back/sides:
works. But without rigging, **raising an arm won't move the sleeve**, and the mesh
does not drape/fold like fabric — it may clip at shoulders/arms ("paper-doll").
Accepted for v1 (fabric realism + limb-following are later refinements, needing
rigged garments — Wanna's moat). Rigid categories (eyewear/jewelry/accessories/
shoes) look good immediately.

## 7. Error handling & edge cases

- Camera permission denied → clear message + retry.
- Low-end device / low fps → degrade gracefully (lower tracker rate; still usable).
- Product has no GLB yet → hide try-on for that product (or show 3D viewer only).
- Tracker loses the body part (out of frame) → freeze/hide model, prompt to reframe.
- No test suite in repo (per CLAUDE.md) → type-checking + manual device QA.

## 8. Out of scope (v1)

- AI image generation / diffusion try-on (explicitly rejected).
- Any server-side GPU rendering.
- True cloth simulation / rigged deformable garments.
- Fully-automatic 3D for the entire catalog (v1 = curated set).
- Native mobile app; paid AR SDKs (Perfect Corp/WANNA, Banuba, Geenee, 8th Wall).

## 9. Rough 10-day plan

- **D1–2:** Testing harness backend (§5b): Tripo3D build job in MediaServing
  (endpoint + queue + worker + S3 folder + status). Get one GLB built from
  front/back/side photos end-to-end.
- **D1–2 (parallel):** Scaffold `tryon/` engine: r3f scene + camera background +
  load a GLB. Fix rear-camera bug. Category picker.
- **D3–4:** Test page (§5b) + Eyewear (FaceLandmarker + GLB + occluder) — flagship;
  validate Tripo3D eyewear quality on the harness.
- **D4–5:** Neck + wrist accessories (Face/Pose/Hand trackers, same engine).
- **D5–7:** Top + bottom clothing (PoseLandmarker + full-mesh GLB + orientation
  rotation §6 + segmentation occlusion); validate turn-around/back on the harness.
- **D7–8:** Curate the showcase set via the harness; QA models; tune anchors.
- **D8–9:** Shoes (WebAR.rocks footVTO + Tripo3D shoe GLB) if time; else defer.
- **D9–10:** Device testing, polish, buffer.
- **Later (out of scope):** move the build trigger to product upload (§5b migration).

## 10. Risks

- **Tripo3D quality** on thin eyewear/shiny jewelry — QA the showcase set early.
- **Clothing paper-doll** perception — set expectations; lead demos with eyewear.
- **Per-category anchor calibration** (scale/orientation) is fiddly — budget tuning
  time; store calibration in `categoryConfig.ts` + per-GLB metadata.
- **WebAR.rocks foot quality** (shoes) — validate on target devices; keep it phase 2.
- **Device performance** (WebGL + ML on mid/low phones) — test early, degrade.
