# Listing and filters — Production readiness

**Status:** 🟡 Ready with conditions
**In one line:** Listing, boutique page, filters, sort, search and share all work, but the TLS check must be fixed, the price filter in the filter panel needs a flag turned on, and price sorting is wrong for countries with their own price.
**Checked:** branch `development`, commit `6a0265a1`, 2026-10-20 — from the code only.

## What this section is
The shopper sees a grid of products with a filter bar on top. Three routes use the same grid:
- `/{lang}/filters/...` — the boutique page (`/filters/boutiques/{slug}`) and any filter or search result. A link opened from inside the app shows the same page as an overlay (`@modal/(.)filters`).
- `/{lang}/featured/...` and `/{lang}/flashDeals/...` — reached from the row headers on the home page.
The bar holds a back button, an in-listing search box, sort, the filter panel button and share.

## ⚠️ Works, with limits
- **L-1 — Pages read the live index, not a fixed snapshot.** `ELASTIC_LISTING_PIT` is off (`services/elastic/elasticSearch.ts:151`). While the index changes, a product can be skipped between two pages. Repeats are removed in the browser. If the flag is turned on, every first listing page opens a snapshot that lives 2 minutes (`ELASTIC_LISTING_PIT_KEEPALIVE`) and is never closed early.
- **L-2 — Without `LISTING_PRICE_AGG_ENABLED`, the price bands in the chip row come from the first 10 products only** (4 equal bands, `services/elastic/helpers.ts:960-1030`). They do not cover the whole result. With the flag on, they cover every matching product.
- **L-3 — Product totals stop at 10,000** (`track_total_hits: 10000`, `services/elastic/elasticSearch.ts:308`).
- **L-4 — Listing pages are not cached.** All three routes still set `instant = false`. Each view runs the main search, a second search for child categories, and on a boutique page one more for the boutique.
- **L-5 — Every page of a 2+ word search calls the AI model again**, including each "load more" page and each filter-panel count (`services/elastic/elasticSearch.ts:240`). This adds up to 6 s per call and costs AI quota. Without `GEMINI_API_KEY` the search still works on the raw text.
- **L-6 — Elasticsearch lags the backend by a few seconds.** A product just added or edited may not list yet. This is not a lost write.
- **L-7 — The flash-deals page uses whole UTC days** (`now/d`, `services/elastic/helpers.ts:1516-1517`), and staging often has no deal at all.
- **L-8 — Some sorts depend on index fields.** Best sellers uses `orders_count`, New/Oldest use `created_at`. If a field is missing in the index, the sort falls back to id order with no error (`unmapped_type`). Name sort runs a script, which is slower on big results.
- **L-9 — Related categories disappear from the chip row during a typed search** until the next filter tap (`components/Server/FilterListReactive.tsx:83`).
- **L-10 — Currency depends on Redis.** If the Redis read throws, the listing gets no currency (`components/Listing/FiltersPageContent.tsx:70-103`); the browser then formats prices with the currency kept in its store.
- **L-11 — Unknown words in a `/filters/...` address are ignored**, so the page shows the whole catalogue instead of a 404.

## ❓ Needs confirmation from the backend team
- Can the index carry one sortable price per country (for example the country offer price at the top level)? Without it, price sort cannot be right in countries with their own price (M-3).
- Do the production indexes have `orders_count`, `created_at`, `custom_products.name.keyword` (nested), `country_offer_prices` and `custom_boutiques.slug.keyword`? The QA rule fails loudly if the last one is missing; the sorts fail quietly.
- Are flash-deal `start_date` / `end_date` stored in UTC?
- If `ELASTIC_LISTING_PIT` is turned on: what is the cluster limit for open snapshots, and is 2 minutes per listing session acceptable?
